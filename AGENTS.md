# AGENTS.md

## Project mission

Build a production-quality cross-platform research application for iOS and Android that collects motion-sensor datasets reliably, even without network connectivity.

The system must be easy for two groups:

1. **Participants / final users** — minimal steps, clear instructions, no technical concepts exposed.
2. **Researchers / admins** — easy participant management, protocol configuration, dataset monitoring, export, and versioning without editing source code.

The experiment protocol will change over time. The acquisition system must therefore be **configuration-driven**, not hard-coded.

---

## Required architecture

Use this architecture unless there is a strong technical reason to deviate. If you deviate, document the reason in `docs/ARCHITECTURE_DECISIONS.md`.

### Mobile app

- Flutter / Dart for shared iOS + Android UI and application logic.
- Native Kotlin on Android for sensor acquisition using `SensorManager`.
- Native Swift on iOS for sensor acquisition using Core Motion.
- Drift + SQLite for local application state and metadata.
- Raw sensor samples are first written locally to files.
- Recording must continue correctly with no internet connection.
- Upload happens only after a trial is safely closed locally.

### Backend

- Supabase PostgreSQL for centralized metadata.
- Supabase Auth for researcher/admin authentication.
- Supabase Edge Functions for privileged server-side operations.
- Cloudflare R2 for raw sensor files.
- Do not insert every raw sensor sample as a PostgreSQL row.

### Admin interface

Use Flutter Web unless an implementation blocker makes another web framework clearly preferable.

Admins must be able to:

- create/manage studies;
- create/manage pseudonymous participants;
- generate participant codes and QR enrollment data;
- configure protocols from a UI;
- create/edit protocol drafts;
- validate protocols before publishing;
- publish immutable protocol versions;
- view participant/session/trial progress;
- inspect device/sensor metadata;
- see failed or pending uploads;
- export dataset metadata and raw files.

## Dataset requirements

The raw collection layer must support, when available on the physical device:

- accelerometer;
- gyroscope;
- gravity;
- rotation/orientation data;
- magnetometer;
- native monotonic sensor timestamps.

For every participant, support metadata including:

- pseudonymous participant identifier;
- sex;
- dominant hand.

For every trial, support metadata including:

- session;
- trial identifier;
- gesture/task identifier;
- prompt;
- repetition number;
- hand actually used;
- posture;
- task type, including practice/genuine/impostor when applicable;
- physical device identifier;
- app version;
- protocol version;
- schema version.

For hardware/device metadata, collect where available:

- physical device UUID generated by the app;
- device model;
- manufacturer/vendor;
- OS and OS version;
- sensor name;
- sensor vendor;
- requested sampling rate;
- observed sampling rate;
- sensor resolution/range when available.

For quality metadata, calculate at minimum:

- gesture duration;
- mean sampling rate;
- sampling-rate standard deviation;
- dropped/estimated missing samples where meaningful;
- inter-sample interval statistics;
- sample counts by sensor.

## Identity model

The following concepts are different and must never be conflated:

- `participant_id`: pseudonymous person in the study;
- `session_id`: one study session for a participant;
- `trial_id`: one recorded task/repetition;
- `physical_device_id`: one actual phone installation/device;
- `gesture_id` / `task_id`: configured task definition.

Use UUIDs internally.

Participants do **not** need normal user accounts.

A participant is resolved through a short participant code or QR enrollment token. The same participant can therefore be opened on multiple physical phones while keeping the same `participant_id`.

Researchers/admins use Supabase Auth.

Never use real participant names, emails, student IDs, or other direct identifiers as the primary participant identifier.

## Protocol engine rules

The protocol is data, not source code.

Never implement experiment flow with hard-coded branches such as:

```dart
if (session == 1) {
  collectInitials();
}
```

Instead, use a versioned protocol model.

A protocol must be able to describe at least:

- sessions;
- ordered tasks;
- prompts/instructions;
- gesture/task IDs;
- repetition count;
- posture;
- required hand;
- device role such as `personal`, `phone_a`, `phone_b`;
- task type;
- optional preparation instructions;
- optional practice trials;
- optional randomization/order metadata if later required.

The mobile app downloads the active/pinned protocol version and caches it locally.

A session must continue using the protocol version it started with, even if a newer version is published while the session is in progress.

Published protocol versions are immutable.

Editing a published protocol creates a new draft/version.

## Recording rules

Reliability is more important than convenience.

### Required state machine

Implement an explicit recording state machine such as:

- `idle`
- `ready`
- `countdown`
- `recording`
- `stopping`
- `validating`
- `saved`
- `failed`

Guard against invalid transitions and double taps.

### Sensor timestamps

Use native sensor timestamps.

Do not replace sensor timestamps with the time at which Flutter receives an event.

Store timestamps at sufficient precision, preferably nanoseconds where the platform provides it.

### Raw storage

During recording:

1. receive native sensor callbacks;
2. buffer a small number of samples natively;
3. write batches to a local raw file;
4. do not perform one Flutter/SQLite insert per sample.

Recommended normalized raw columns:

```text
timestamp_monotonic_ns,sensor_type,x,y,z,w,accuracy
```

`w` is optional and useful for quaternion rotation data.

After a trial:

1. close/flush the file;
2. compute quality statistics;
3. gzip the raw file;
4. calculate SHA-256;
5. persist local trial metadata;
6. mark the trial as safe locally;
7. only then queue network synchronization.

The UI may show "Saved" only after local persistence succeeds.

---

## Local-first synchronization

Use a durable sync state machine:

- `local`
- `queued`
- `uploading`
- `synced`
- `failed`

Rules:

- network availability must not affect the recording process;
- failed uploads remain locally available;
- retry uploads later;
- never delete the only local copy before remote verification succeeds;
- sync operations must be idempotent;
- restarting/killing the app must not corrupt sync state;
- the app must recover pending uploads after restart.

---

## Remote storage rules

Supabase stores metadata.

Cloudflare R2 stores raw sensor files.

Suggested object layout:

```text
study/<study_uuid>/<participant_uuid>/<session_uuid>/<trial_uuid>/sensors.csv.gz
```

Do not put real names, participant codes, email addresses, or other direct identifiers in object paths.

Store file metadata in Supabase, including:

- object key;
- size;
- SHA-256;
- MIME/content type;
- upload status;
- created/uploaded timestamps.

## Security rules

### Never place privileged secrets in the mobile or web client

The following must never be embedded in Flutter client code or committed:

- `SUPABASE_SERVICE_ROLE_KEY`
- `R2_ACCESS_KEY_ID`
- `R2_SECRET_ACCESS_KEY`
- any private signing secret

The mobile/web client may contain only client-safe configuration such as:

- `SUPABASE_URL`
- `SUPABASE_ANON_KEY`
- public application configuration.

Use Supabase Edge Functions or another trusted server-side environment to access privileged keys.

For R2 uploads:

1. authenticated client requests an upload authorization/signed URL;
2. server validates permission and intended object key;
3. server creates a short-lived signed upload URL;
4. client uploads directly to R2;
5. client/server finalizes metadata after verification.

Enable Row Level Security on Supabase tables.

Do not rely on hidden UI controls as authorization.

## Environment files

Create these files if they do not exist:

### Root/client `.env.example`

```dotenv
APP_ENV=development

SUPABASE_URL=
SUPABASE_ANON_KEY=
SUPABASE_EDGE_FUNCTIONS_URL=

ENABLE_DEBUG_TOOLS=true
```

Create `.env` locally from `.env.example`, but `.env` must be in `.gitignore`.

### Server secrets example

Create:

`supabase/functions/.env.example`

```dotenv
SUPABASE_URL=
SUPABASE_SERVICE_ROLE_KEY=

R2_ACCOUNT_ID=
R2_BUCKET_NAME=
R2_ACCESS_KEY_ID=
R2_SECRET_ACCESS_KEY=
R2_ENDPOINT=
```

The real server secrets file must be gitignored.

Never fabricate real credentials.

If credentials are not available, use placeholders/mocks and continue implementing everything that does not require a live service.

## User experience requirements

### Participant mode

The participant UI must remain simple.

Typical flow:

1. scan QR or enter participant code;
2. show study/session context;
3. show one task at a time;
4. clearly show posture/hand/device instructions;
5. explicit ready/start/countdown;
6. explicit recording state;
7. explicit stop when required;
8. confirmation that the trial is safely saved;
9. move to the next repetition/task.

Do not expose:

- UUIDs;
- database names;
- cloud storage paths;
- sampling configuration unless the researcher explicitly enables a diagnostic screen;
- backend terminology.

The UI must prevent accidental double-start/double-stop.

### Researcher/admin mode

Admins should not need to hand-edit JSON for routine protocol changes.

Provide forms, validation, preview, draft/publish workflow, and version history.

Raw JSON import/export may exist as an advanced option.

## Database model

Create migrations for a relational model covering at least:

- `studies`
- `researcher_profiles`
- `study_members`
- `participants`
- `physical_devices`
- `protocols`
- `protocol_versions`
- `sessions`
- `trials`
- `trial_files`

All core records should use UUID primary keys.

Use foreign keys, useful indexes, timestamps, and RLS policies.

Keep database migrations version-controlled.

## Testing requirements

Do not consider a feature complete without appropriate tests.

### Unit tests

Cover at least:

- protocol parsing;
- protocol validation;
- trial queue generation;
- recording state-machine transitions;
- sync state-machine transitions;
- quality-metric calculations;
- file checksum logic;
- data serialization.

### Integration tests

Cover, with mocks/local services where needed:

- participant lookup/enrollment;
- session creation;
- protocol caching;
- fake trial recording pipeline;
- local persistence;
- sync queue;
- successful upload finalization;
- failed upload + retry;
- app restart with pending uploads.

### Manual hardware test plan

Document tests for:

- at least two Android device/manufacturer families;
- at least two iPhone generations where possible;
- app background/foreground;
- phone call/interruption;
- network loss during/after recording;
- app process death after local save;
- low storage;
- unavailable sensor;
- slow or unusual sampling rate.

## Code quality

- Keep domain logic independent from UI.
- Prefer explicit interfaces/adapters for backend, local DB, storage, and sensor access.
- Avoid global mutable state.
- Keep platform-specific code behind a clean Dart interface.
- Use typed models.
- Use migrations, not manual database editing.
- Format code before finishing a task.
- Run static analysis and tests.
- Do not leave generated secrets in logs or test fixtures.
- Avoid TODOs for critical correctness/security behavior. If a TODO is unavoidable, record it in `docs/PROGRESS.md`.

## Autonomous work rules for Codex

Work through `IMPLEMENTATION_PLAN.md` in order.

Do not wait for the user between normal engineering steps.

Only stop and ask the user when a decision or manual action cannot safely be inferred, such as:

- real Supabase project credentials are required to perform a live deployment/test;
- real Cloudflare R2 credentials are required to perform a live deployment/test;
- Apple/Android signing requires account-specific certificates or identifiers;
- a destructive production operation needs confirmation;
- a product requirement is genuinely ambiguous and materially changes stored data or privacy behavior.

For missing credentials:

- implement the adapter;
- create `.env.example`;
- add validation for missing environment variables;
- provide mocks/fakes;
- test locally;
- document the exact values the user must later provide;
- continue with the rest of the plan.

At the end of every phase:

1. run formatting;
2. run static analysis;
3. run relevant tests;
4. fix failures;
5. update `docs/PROGRESS.md`;
6. update `docs/ARCHITECTURE_DECISIONS.md` if architecture changed;
7. make a concise summary of files changed and remaining blockers.

Never silently skip a failed test.

---

## Definition of done

The first production-ready milestone is complete when:

- iOS and Android can record required sensor streams locally;
- recording works offline;
- raw trials survive app restarts;
- participant UUID is stable across multiple phones through central enrollment;
- admins can configure and publish versioned protocols without changing source code;
- a participant session is generated from a protocol;
- local trial metadata and files sync reliably;
- raw files upload to R2 through server-authorized signed uploads;
- metadata is stored in Supabase;
- RLS/security boundaries are implemented;
- dataset export works;
- quality metrics are generated;
- tests pass;
- setup/deployment documentation is complete.
